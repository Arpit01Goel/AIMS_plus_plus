Integrated Plan: Backend + Roles for AIMS++

Goal
Build a unified backend (Supabase Postgres + Prisma + NextAuth) with full role support (STUDENT, INSTRUCTOR, ADVISOR, ADMIN), and wire it cleanly into routing, layouts, and API routes for all existing portals. Student APIs ship first, but the data model and auth are role-complete from day one.

-------------------------------------------------------------------------------
1. Foundation: Database, Prisma, and Shared Utilities

- Choose and finalize Supabase project and set DATABASE_URL in env (as outlined in AUTHENTICATION_SETUP.md).
- Add Prisma dependencies and bootstrap schema:
	- Install prisma and @prisma/client.
	- Add prisma/schema.prisma with a PostgreSQL datasource pointing at Supabase.
- Create a shared Prisma client helper:
	- Add src/lib/db.ts exporting a singleton Prisma client for all server-side data access.
- Establish a basic migration workflow:
	- Run prisma migrate dev to create and evolve the schema.
	- Add a simple seed script (e.g., prisma/seed.ts) to create initial test data for each role.

-------------------------------------------------------------------------------
2. Identity & Roles: Core Models and NextAuth Types

2.1 Role model and enums
- Define a Role enum in Prisma: STUDENT, INSTRUCTOR, ADVISOR, ADMIN.
- Keep authorization logic focused around this single role field (no complex permissions system yet, but schema must be extendable).

2.2 User and role-specific profile models
- In prisma/schema.prisma, define:
	- User
		- id, email (unique), passwordHash (nullable for pure OAuth), name, image, role (Role enum), createdAt, updatedAt.
	- Student
		- 1:1 with User (userId unique), fields like entryNumber, programId, departmentId, batch, phone, etc., mirroring the student profile UI.
	- Instructor
		- 1:1 with User (userId unique), fields like title, departmentId, officialEmail.
	- Advisor
		- 1:1 with User (userId unique), relation to Department/Program and optional metadata (primaryCohort, notes, etc.).
	- (Optional) AdminProfile
		- 1:1 with User (userId unique), used later for finer-grained admin capabilities and audit behavior.
- Supporting identity-linked models:
	- Department (code, name).
	- Program (code, name, level, departmentId).

2.3 NextAuth type extensions (multi-role aware)
- In src/types/next-auth.d.ts, extend:
	- User: add role, optional studentId, instructorId, advisorId.
	- Session.user: same fields as User so the client can branch on role.
	- JWT: role plus role-specific IDs to avoid extra DB round-trips in APIs.

-------------------------------------------------------------------------------
3. Auth Flows: NextAuth, Sign-In, OTP, and Session Shaping

3.1 NextAuth core configuration
- In src/lib/auth.ts:
	- Use Prisma (and/or PrismaAdapter if needed) to look up and persist User records.
	- Configure credentials provider (email + password) and Google OAuth provider.
	- In the authorize/signIn logic:
		- Find or create a User by email.
		- Ensure every created user has a valid role (STUDENT by default for student signups; others seeded or created via admin flows).
		- For student signups, also create a Student profile record (Program/Department may be default/placeholder initially).
	- Implement callbacks:
		- jwt callback: copy user.role and role-specific IDs (studentId, instructorId, advisorId) from the DB; keep them in token.
		- session callback: mirror token.role and IDs onto session.user so layouts and APIs can read them.

3.2 API route for NextAuth
- In src/app/api/auth/[...nextauth]/route.ts:
	- Export the NextAuth handler configured in src/lib/auth.ts.
	- Ensure the same Prisma-based user lookup/creation logic is used for both credentials and Google providers.

3.3 OTP and password reset (all roles)
- Extend Prisma schema:
	- OTPCode (id, userId or email, code, purpose, expiresAt, consumedAt, createdAt).
	- (Optional) PasswordResetToken (id, userId, token, expiresAt, usedAt) for link-based flows.
- Update src/lib/otp.ts to use Prisma:
	- Generate codes and store them in OTPCode instead of in-memory.
	- Validate codes by checking user/email, purpose, and expiry; mark codes as consumed.
- Wire into existing auth API routes:
	- src/app/api/auth/send-otp/route.ts: insert OTPCode and send via email (src/lib/email.ts).
	- src/app/api/auth/verify-otp/route.ts: verify OTPCode and respond with a short-lived token or flag.
	- src/app/api/auth/reset-password/route.ts: validate OTP/Reset token, then update User.passwordHash using secure hashing.
- Ensure OTP flows are role-agnostic: any user (student, instructor, advisor, admin) can reset their password with the same mechanisms.

-------------------------------------------------------------------------------
4. Authorization & Routing: Middleware and Role-Aware Layouts

4.1 Global middleware for protected areas
- Add a root middleware.ts:
	- Use NextAuth server helpers (getToken or getServerSession-like utility) to read JWT for each request.
	- Protect all portal routes:
		- /student/(portal)/** → require role === 'STUDENT'.
		- /instructor/(portal)/** → require role === 'INSTRUCTOR'.
		- /advisor/(portal)/** → require role === 'ADVISOR'.
		- /admin/(portal)/** → require role === 'ADMIN'.
	- Behavior:
		- If unauthenticated, redirect to /auth/login (existing login route).
		- If authenticated but role mismatch for that segment, optionally redirect to the correct portal home or show a 403/“Not allowed” page.

4.2 Role-aware layouts and navigation
- In portal layouts (e.g., src/app/student/(portal)/layout.tsx, instructor/(portal)/layout.tsx, advisor/(portal)/layout.tsx, admin/(portal)/layout.tsx):
	- Use getServerSession to fetch the current session.
	- If no session or wrong role, redirect to /auth/login (middleware should normally catch this, but layout is a second safety net).
	- Use session.user.role and role-specific IDs to conditionally show navigation items and links.
- If desired later, factor out shared shell (sidebar/topbar) into a common layout component that receives the role and menu configuration.

-------------------------------------------------------------------------------
5. Domain Modeling: Academics, Enrollment, Fees, Feedback, Calendar

5.1 Academic structure
- In Prisma schema, add role-neutral academic models:
	- AcademicSession
		- code (e.g., 2025-II), startDate, endDate, isCurrent.
	- Course
		- code, title, credits, ltpsc, departmentId, category, etc.
	- CourseOffering
		- id, courseId, academicSessionId, primaryInstructorId (Instructor), capacity, slot, etc.
	- CourseMeeting
		- offeringId, dayOfWeek, startTime, endTime, location; aligns with timetable UI.
	- Enrollment
		- studentId, offeringId, status (ENROLLED, DROPPED, WAITLISTED), grade (if finalized), attendancePercentage, etc.

5.2 Relationships to roles
- Student
	- Has many Enrollment entries (one per CourseOffering).
- Instructor
	- Linked to CourseOffering (primary and/or via a join table for multiple instructors).
- Advisor
	- Linked to Student via a relation (advisor-of) and/or to Program/Department.

5.3 Financial and academic artifacts
- FeeReceipt
	- id, studentId, amount, category, paidOn, storagePath (Supabase Storage path), createdAt.
- FeedbackQuestion
	- id, courseId (or global), text, questionType, isActive.
- CourseFeedbackResponse
	- id, questionId, enrollmentId or (studentId + offeringId), rating/text, createdAt.
- AcademicEvent
	- id, title, description, startDate, endDate, type, visibility (e.g., STUDENT_ONLY, ALL), createdAt.

-------------------------------------------------------------------------------
6. Student-Facing APIs (MVP Using Full Role Model)

For each API under src/app/api, use NextAuth server helpers to read the session and enforce role === 'STUDENT', scoping queries by session.user.studentId.

6.1 Profile
- /api/profile
	- GET: returns merged User + Student + Program + Department data matching student profile UI.
	- PATCH/PUT: updates allowed profile fields (phone, address, etc.), not email/role.

6.2 Records, courses, timetable
- /api/records
	- Returns current and past courses/enrollments with grades, ltpsc, credits, and academic session info, shaped for records/page.tsx.
- /api/student/timetable
	- Returns the weekly timetable for the student’s current enrollments (CourseMeeting entries grouped by day and time).
- /api/courses
	- Returns available CourseOfferings for the current AcademicSession, including instructor names, slots, categories, and whether the student is already enrolled.
- /api/courses/enrolled
	- Returns the student’s current enrollments and minimal course info for the “My Courses” view.

6.3 Enrollment actions
- /api/enrollments
	- POST: enroll the current student in a CourseOffering (if capacity and rules allow).
	- PATCH: change status (e.g., drop a course) or update derived fields if needed.
	- DELETE: optional hard delete for test/demo; in production, typically prefer status changes.
- Always validate against business rules: session window, capacity, duplicate enrollments, etc. (can be relaxed for initial MVP).

6.4 Fees
- /api/fees
	- GET: list all FeeReceipts for the current student.
	- POST: create a new fee record and (optionally) generate a Supabase Storage upload URL for the receipt file.
	- DELETE: remove a fee entry (for admin/testing; may later be admin-only).

6.5 Feedback
- /api/feedback/courses
	- Lists courses the student can currently give feedback on, with questions.
- /api/feedback/submit
	- Accepts responses for one course (one or many questions) and writes CourseFeedbackResponse entries scoped to the student’s enrollment.

6.6 Calendar
- /api/calendar/events
	- Returns AcademicEvent entries visible to students, optionally filtered by date range.

-------------------------------------------------------------------------------
7. Instructor, Advisor, and Admin APIs (Scaffolding Now, Build Later)

Even if the UI is not ready, define namespaced APIs and minimum queries so future portals can plug in without schema churn.

7.1 Namespaces and basic endpoints
- /api/instructor/* (role === 'INSTRUCTOR')
	- /api/instructor/courses: list CourseOfferings taught by the current instructor.
	- /api/instructor/courses/[offeringId]/students: list enrolled students with basic info and grades/attendance.
- /api/advisor/* (role === 'ADVISOR')
	- /api/advisor/advisees: list students assigned to the advisor.
	- /api/instructor/advisor/approvals: list pending CourseApprovalRequests if modeled.
- /api/admin/* (role === 'ADMIN')
	- /api/admin/users: basic user listing and role management (initially read-only).
	- /api/admin/academics: simple endpoints to list/create Departments, Programs, Courses, and AcademicSessions.

7.2 Authorization patterns
- In each handler:
	- Validate session first; ensure role matches the namespace (INSTRUCTOR/ADVISOR/ADMIN).
	- Scope queries by instructorId or advisorId where relevant.
	- Return simple but realistic JSON shapes that UIs can adopt later.

-------------------------------------------------------------------------------
8. Auditing and Safety Nets

- Add optional audit fields to sensitive models:
	- Enrollment: createdByUserId, updatedByUserId.
	- FeeReceipt: createdByUserId.
	- AdvisingAppointment / CourseApprovalRequest (if added): approvalByUserId, statusChangedByUserId.
- In APIs where admins or faculty mutate data, set these fields using session.user.id.
- Add basic error handling patterns:
	- Standardize JSON error responses with status and message.
	- Avoid leaking internal details (e.g., Prisma errors) to the client.

-------------------------------------------------------------------------------
9. Milestones and Implementation Order

Phase 1 – Schema & Plumbing
- Implement Prisma schema for User, Role enum, Student/Instructor/Advisor profiles, Departments, Programs.
- Set up Prisma client (src/lib/db.ts), migrations, and a basic seed script with one user per role.

Phase 2 – Auth, Roles, and OTP
- Implement NextAuth configuration in src/lib/auth.ts with Prisma integration.
- Extend next-auth.d.ts types for role and role-specific IDs.
- Implement OTP/Reset flows backed by Prisma and wire them into existing auth API routes.

Phase 3 – Routing Protection & Layouts
- Add middleware.ts to protect portal routes by role.
- Update student/instructor/advisor/admin portal layouts to use getServerSession and enforce correct role & navigation.

Phase 4 – Student APIs
- Implement /api/profile, /api/records, /api/student/timetable, /api/courses, /api/courses/enrolled, /api/enrollments, /api/fees, /api/feedback/*, /api/calendar/events.
- Update student portal pages to consume these APIs instead of hard-coded data.

Phase 5 – Faculty/Advisor/Admin Scaffolding
- Implement minimal /api/instructor/*, /api/advisor/*, /api/admin/* endpoints with proper role checks.
- Optionally connect one or two admin or faculty portal pages to these endpoints as vertical slices.

Phase 6 – Hardening & Refinement
- Refine validation rules (enrollment constraints, fee operations, feedback windows).
- Tighten error handling, add audits, and clean up any schema/API gaps discovered while wiring up the UIs.
